# 0001. サーバは事実を渡し、クライアントが解釈する

状態: 採用（2026-11-03）

## 背景

プロトコルは、クライアントをサーバの保存形式やデコードから切り離す。サーバの仕事には、録画の形式やユーザー型に依存するものがある。デコード、フィールドの取り出し、Hahn 型への変換、どのフィールドが計測時刻かの判定、座標変換が静的か動的かの分類である。一方、依存しないものもある。座標変換の補間、ある時刻でのフレームの木の解決、位置合わせにどの時刻を使うかの選択である。

別言語でのサーバ実装は目標にしない。したがって「サーバごとに同じ処理を実装し直さずに済むようにする」ことは、処理の置き場所を決める理由にならない。決め手はクライアントでの融通である。3D 表示では、利用者が次のことをしたくなる。

- 補間を切り、記録されたサンプルだけを見る
- 位置合わせを記録時刻と計測時刻のどちらで行うか選び、見比べる
- 基準の座標系を切り替える

サーバが座標変換を解いて結果を返す場合、これらの選択肢を提供すると、選択肢ごとにリクエストの指定が増え、仕様とテストの組み合わせが増え、画面で切り替えるたびにサーバへの問い合わせが要る。

## 決定

- サーバは、録画の形式やユーザー型の知識が要るものを、録画から読み取った事実として渡す。変換した値、記録時刻と計測時刻を区別した時刻、座標変換のサンプル、静的か動的かの分類である。
- クライアントは、利用者が画面で選べる解釈を受け持つ。補間、位置合わせに使う時刻、基準の座標系などである。
- 補間のように細かい規則がある処理は、Rust で一度書き、WebAssembly でクライアントでも動かしてよい。そうするかどうかは実装上の選択であり、この決定には含めない。

## 結果

- 座標変換は、サーバがサンプルを渡し、クライアントが解く方式にする。詳細は座標変換の ADR で決める。
- クライアントは、解いた結果ではなく、範囲内の座標変換のサンプルを受け取る。通信量が増え得るので、範囲と量の上限をその ADR で検討する。
- データを読み込んだあとは、画面での選択がサーバへの問い合わせなしに反映される。
- 解釈の規則は、それを実行する実装（クライアント、または共有する Rust の実装）でテストする。

## 採らなかった案

- サーバで解き、選択肢ごとにリクエストの指定を足す。上に書いた指定の増加と問い合わせの往復のため採らない。
