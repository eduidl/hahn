# 0010. クライアントのデータ取得は一つのデータアクセス層にまとめ、ウィジェットは必要なものを宣言する

状態: 提案（2026-11-10）

[0003](0003-transforms.md)、[0008](0008-errors.md)、[0009](0009-batched-views.md) を前提とする。

## 背景

クライアントの画面には複数のウィジェットが並ぶ。それぞれのウィジェットは、録画から読んだデータを次のどれかの形で使う。

- メッセージのフィールドの全履歴（グラフ、表など）
- 再生位置の周りの値（生のメッセージ、画像、点群など）
- ある時刻より前の最後の値（まれにしか記録されないトピックや、録画の初めに一度だけ記録されたキャリブレーションなど）
- run・グループ・トピック・フレームの一覧などのメタ情報
- 座標変換のサンプル（[0003](0003-transforms.md)）

同じデータを複数のウィジェットが同時に使うことは多い。同じトピックのグラフと表を並べる、画像と、その画像に重ねる点群を同じ時刻で表示する、といった場合である。また、あるフィールドを読めば、その下のフィールドの値も分かる。

録画は数時間に及び、画像や点群は1件で数 MB になる。データを何度も読んだり、ウィジェットごとに重複して持ったりすると、サーバの負荷・通信量・メモリがウィジェットの数だけ増える。再生中は再生位置がアニメーションのフレームごとに変わるので、要求をそのまま送るとリクエストが溜まり、追いつかなくなる。

取得とキャッシュをウィジェットごとに書くと、重複の排除、中止、解放、エラーの扱いがウィジェットごとに異なり、同じ不具合をウィジェットの数だけ直すことになる。

## 決定

### 層

- データは「ウィジェット → データアクセス層 → サーバ」の順に流れる。
- サーバへリクエストを送るのはデータアクセス層だけとする。ウィジェットは URL、リクエスト、応答の形式、キャッシュを扱わない。
- ウィジェットは、何がどの範囲で要るかを宣言する。データアクセス層は、その時点で分かっている値と状態（読み込み中・完了・失敗）を返し、変化があれば通知する。

### 単位と寿命

- データアクセス層は、開いている run ごとに一つのストアを持つ。run を閉じるか切り替えると、ストアと、その保持するデータを捨て、実行中のリクエストを中止する。
- ストアは画面のコンポーネントの木を通して渡す。モジュールの大域変数には置かない。寿命が run の開閉と一致し、テストごとに独立したストアを使えるようにするためである。
- ストアは画面の描画の仕組みに依存しない。描画の仕組みとの接続は、ストアを購読する薄い層に分ける。

### 要求の表し方

要求は、資源と取り方の組で表す。

- **資源**: メッセージのフィールド（グループ・トピック・フィールドの道筋）、ビュー（グループ・トピック・ビュー）、run の座標変換、メタ情報。
- **取り方**: 全履歴、時刻の範囲、ある時刻より前の最後の値。

時刻の範囲は、資源の種類ごとに決めた固定の境界にそろえる。境界をそろえると、異なるウィジェットの要求や、前後へのシークで同じ範囲を使い回せる。

### 共有

- 同じ資源・同じ取り方の要求には、一つのリクエストだけを送る。実行中のリクエストがあれば、後から来た要求もそれに相乗りし、それまでに受け取った分から受け取る。
- 読んだ範囲や親を含む要求には、新たに読まずに既にあるデータから答える。全履歴を読み終えていれば、その中の時刻の範囲の要求にも、それで答える。親のフィールドを読み終えていれば、子のフィールドもそこから取り出す。
- 値は資源ごとに一度だけ持ち、それを使うウィジェットの間で共有する。ウィジェットは受け取った値を自分用に複製しない。
- 同じグループ・同じ時刻範囲の小さいビューをまとめて取得する処理（[0009](0009-batched-views.md)）も、データアクセス層の中で行う。同じ資源の要求は、まとめる前に一つにする。

### 保持と解放

- ウィジェットは、使っている間だけ資源を保持し、使わなくなったら手放す。
- 全履歴は、誰も保持しなくなったら捨てる。
- 時刻の範囲は、誰も保持しなくなっても、資源の種類ごとの上限まで残す。直前の位置に戻るシークで読み直さないためである。保持されているものは上限を超えても捨てない。上限を超えたら、保持されていないもののうち再生位置から遠いものから捨てる。
- リクエストは、相乗りしている要求がすべて去ったときに中止する。一つのウィジェットが去っても、ほかのウィジェットのリクエストは止まらない。

### 部分的な結果と更新の頻度

- ストリームで届くデータは、受け取った分から要求に渡す。読み終わるまで待たない。
- 変化の通知は間引く。ストリームの1回の受信ごとにすべてのウィジェットを描き直さないためである。

### 再生位置への追従

- 再生位置に追従する要求は、同時に一つまでしか送らない。応答を待つ間に位置が変わったら、最後の位置だけを次に送り、間の位置は送らない。
- 新しい値が届くまでは、再生位置より後でない限り直前の値を表示し続ける。
- 再生位置の値がまだ無いことを、再生の制御に伝える。再生の制御は、値が揃うまで再生を待つかどうかをそれで決める。
- 再生位置の先の範囲を、再生の向きに少し先読みする。

### エラー

- 失敗は [0008](0008-errors.md) のコードで識別し、要求の状態として返す。HTTP の失敗もストリーム内の失敗も、同じ形で返す。
- 失敗した要求は、そのまま保持し続けない。次に要求されたときは読み直す。
- 中止は失敗として扱わない。

## 結果

- 同じデータへのリクエストが、ウィジェットの数に関係なく一つになる。メモリ上の値も一つになる。
- ウィジェットは表示に専念できる。新しいウィジェットを加えても、取得やキャッシュを書き直す必要がない。
- 重複の排除、中止、解放、エラーの扱いが一か所にまとまり、データアクセス層を単独で検査できる。サーバの代わりを用意する箇所も一つで済む。
- 一方で、キャッシュの方針がデータアクセス層に集中し、その層は複雑になる。資源と取り方の表し方を誤ると、共有できるはずの要求が共有されない。上限は資源の種類ごとに決める必要があり、大きい全履歴（ビューの全履歴など）はメモリを多く使う。
- 上位のコンポーネントは、ウィジェットが何を使うかを知る必要がなくなる。

## 採らなかった案

- **ウィジェットごとに取得とキャッシュを持つ**: 同じデータを重複して読み、重複して持つ。中止や解放の扱いがウィジェットごとに異なり、揃わない。
- **上位のコンポーネントがすべてのウィジェットの要求を集め、結果を配る**: ウィジェットの種類を加えるたびに上位のコンポーネントを変える必要があり、ウィジェットが何を使うかが、ウィジェットの外に散らばる。表示されていないウィジェットの分まで読み続けやすい。
- **汎用のデータ取得ライブラリのキャッシュに任せる**: 要求を固定のキーで識別する仕組みでは、親のフィールドから子を取り出すこと、全履歴から時刻の範囲を取り出すこと、受信中のストリームへの相乗り、再生位置への追従を表しにくい。必要な部分を結局自分で書くことになる。
- **ブラウザの HTTP キャッシュに任せる**: 実行中のリクエストへの相乗りや、デコード済みの値の共有ができない。範囲を含む要求に答えることもできない。
- **ストアをモジュールの大域変数に置く**: run の開閉とストアの寿命を別々に管理する必要があり、テストの間でデータが残る。
