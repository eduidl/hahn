# 0005. Hahn 型は、1つの値か1つのまとまりかで分け、クライアントが使い道を持つものだけを設ける

状態: 採用（2026-11-03）

[0001](0001-server-delivers-facts-client-interprets.md)、[0002](0002-time-model.md)、[0003](0003-transforms.md)、[0004](0004-camera-calibration.md) を前提とする。

## 背景

時系列やテーブルは、スキーマだけでトピックを表示できる。数値は数値として描けばよいからである。画像や点群はそうはいかない。たとえば画像のデータがどこにあるかは、ユーザー型ごとに違う。そこで Hahn は画像や点群などの共通の型（Hahn 型）を定め、サーバがユーザー型のメッセージをそれに変換する。この変換をビューと呼ぶ。クライアントは Hahn 型だけを扱い、ユーザー型を知らなくてよい。

Hahn 型の設け方には、次の論点がある。

- **履歴の意味**: 車両の姿勢や GNSS の位置のように、1つのメッセージが「いまの1つの値」を持つものがある。その履歴をつなげば軌跡になる。一方、計画経路や地図上の図形のように、1つのメッセージが「まとまり全体」を持つものもある。これは次のメッセージで丸ごと置き換わり、履歴をつないでも意味がない。同じ型で両方を表すと、クライアントは軌跡を描いてよいかを判断できない。
- **型の数**: 型を増やすほど、サーバの変換とクライアントの表示の両方が要る。図形の集まりのような汎用の型を1つ設ければ何でも表せるが、クライアントはそれを描く以上のことができない。
- **ユーザー型の中の標準的な型**: ユーザー型のメッセージが、姿勢などの標準的な型をフィールドとして含むことがある。

## 決定

### 型の設け方

- Hahn 型は、クライアントがその型に固有の使い道を持つ場合にだけ設ける。たとえば、姿勢からは軌跡を描け、画像には点群を投影でき、位置は地図に置ける。
- Hahn 型は、それに変換するユーザー型があるときに設ける。変換するものが無い型は先に設けない。
- どの Hahn 型も、1つのメッセージが持つ内容を表す。最新の値は、それまでに表示したものを丸ごと置き換える。クライアントは値どうしの間で状態を持たない。過去の値が要るときは、履歴として取得する。

### 1つの値の型と、まとまりの型

- **1つの値の型**は、1つのメッセージが「その時点の1つの値」を持つことを表す。クライアントは履歴をつないで軌跡を描いてよい。
- **まとまりの型**は、1つのメッセージが「まとまり全体」を持つことを表す。クライアントは、異なるメッセージの値どうしをつながない。
- 1つの値で表せるものは、まとまりの型で表さない。1つの位置は、要素が1つの図形の集まりではなく、1つの値の型で表す。

### 型の一覧

| Hahn 型 | 種類 | 内容 | 主な使い道 |
|---|---|---|---|
| `image` | 1つの値 | 符号化された画像、または画素の配列 | 表示、点群の投影、3D での配置 |
| `camera_calibration` | 1つの値 | カメラの内部パラメータ（[0004](0004-camera-calibration.md)） | 画像の投影と配置 |
| `pointcloud` | まとまり | 1回の計測の点の集まり | 3D 表示、画像への投影 |
| `position` | 1つの値 | 座標系の中の位置（向きなし） | 3D 表示、軌跡 |
| `pose` | 1つの値 | 座標系の中の位置と向き | 3D 表示、軌跡 |
| `poses` | まとまり | 順序のない姿勢の集まり（パーティクル、複数の物体の姿勢など）。姿勢どうしをつながない | 3D 表示 |
| `path` | まとまり | 順序のある姿勢の並び（計画経路など）。姿勢どうしを線でつなぐ | 3D 表示 |
| `geo_location` | 1つの値 | 地球上の1つの位置（経度・緯度、向きは任意） | 地図表示、軌跡 |
| `geo` | まとまり | 地図上の図形（GeoJSON の地物の集まり） | 地図表示 |
| `bbox3d` | まとまり | 座標系の中の直方体の集まり。各箱は中心の姿勢、大きさ、任意のラベル・スコア・ID を持つ | 3D 表示、画像への投影 |
| `image_annotations` | まとまり | 1枚の画像の上の注釈の集まり。点、折れ線、閉じた折れ線、円、文字を画素座標で表し、各注釈は任意のラベル・スコア・ID を持つ | 画像への重ね描き |

- 空間の値（`image`、`camera_calibration`、`pointcloud`、`position`、`pose`、`poses`、`path`、`bbox3d`）は `frame_id` を持つ。地球上の値（`geo_location`、`geo`）は WGS 84 の経度・緯度で表し、`frame_id` を持たない。`image_annotations` は画像の画素座標で表し、`frame_id` を持つ場合も重ねる画像の決定には使わない。
- どの値も、[0002](0002-time-model.md) に従って記録時刻と計測時刻を持つ。
- 速度や共分散など、Hahn 型が表さない内容は、メッセージのフィールドとして読める。

### 画像への注釈と画像の対応

- `image_annotations` の画素座標は、特定の画像の上の座標である。その画像は `frame_id` では決まらない。同じカメラの未補正と補正済みの画像は `frame_id` を共有し、縮小した画像が別のトピックで記録されることもある。検出結果のトピック名にも、画像との対応を示す慣習が無い。
- そのため、サーバは注釈と画像の対応を示さない。利用者が画像パネルで、重ねる注釈のトピックを選ぶ。クライアントは候補の一覧で、画像と `frame_id` が同じトピックを先に示してよい。
- 画像ごとに重ねる注釈の値は、画像と注釈の両方に `stamp_ns` があれば、`stamp_ns` が一致するものとする。一致するものが無いコマには重ねない。どちらかに `stamp_ns` が無ければ、画像の記録時刻以前で最新のものを重ね、時刻が推定であることを画面に示す。
- 注釈の値は元の画像の大きさを持たないので、大きさの確認はしない。画像の外にはみ出す注釈もそのまま描く。

### ユーザー型の中の標準的な型

- サーバは、ユーザー型のフィールドが標準的な型であれば、そのフィールドからビューを設けてよい。ビューは、どのフィールドから変換したかを示す。
- そのフィールドが `frame_id` や計測時刻を持たない場合は、それを含むメッセージのヘッダから取る。取れなければ、[0002](0002-time-model.md) と同じく計測時刻を省く。`frame_id` が取れなければ、そのフィールドからはビューを設けない。

## 結果

- クライアントは、型の種類だけで軌跡を描いてよいかを判断できる。
- GNSS の位置は `geo_location` として軌跡を描き、GeoJSON の図形は `geo` として丸ごと置き換える。
- `position`、`poses`、`path`、`geo_location`、`bbox3d`、`image_annotations` には変換するユーザー型があるので設ける。ROS の `geometry_msgs/PointStamped`、`geometry_msgs/PoseArray`、`nav_msgs/Path`、`sensor_msgs/NavSatFix`、`vision_msgs` パッケージの `Detection3DArray` と `Detection2DArray`、Foxglove の `PosesInFrame`、`LocationFix`、`ImageAnnotations` などである。`Detection2DArray` の矩形は、4点の閉じた折れ線に変換し、ラベル・スコア・ID を引き継ぐ。
- Foxglove の `PosesInFrame` は経路にも順序のない集まりにも使われ、どちらかを記録から判断できない。経路に使われることが多いので `path` に変換する。クライアントは `path` の線を利用者が消せるようにする。
- 汎用の図形の型（ROS の `visualization_msgs/MarkerArray`、Foxglove の `SceneUpdate` など）は設けない。要る場面が出たら、固有の使い道を持つ型で表せないかを先に検討する。3D の検出結果の箱は、汎用の図形ではなく `bbox3d` で表す。
- `bbox3d` と `image_annotations` は、ID を持っていてもまとまりの型であり、クライアントは ID ごとに軌跡をつながない。

## 採らなかった案

- 順序の有無を印として持つ1つの型（`poses`）で `path` と順序のない集まりを表す。`PosesInFrame` のように印をサーバが決められない変換元があり、型の種類で使い道を決める原則にも合わないため、`path` と `poses` を分ける。
- 2D の検出結果の箱を専用の型（`bbox2d`）にする。画像への注釈と同じく対応する画像を利用者が選ぶ必要があり、重ね描き以外の使い道は注釈のラベル・スコアで足りるため、`image_annotations` にまとめる。
- 1つの型で1つの値とまとまりの両方を表し、地物の種類などでクライアントが軌跡を描くかを決める。型だけで判断できず、クライアントがユーザー型の慣習を推し量ることになるため採らない。
- 汎用の図形の型を1つ設け、すべてをそれで表す。クライアントが描く以上のことをできないため採らない。
- 変換するユーザー型が無い型も、先に一通り設ける。表示と変換の両方が伴わない型は検証できないため採らない。

## 未決

- 追跡 ID を持つ検出結果について、ID ごとの軌跡を描くかどうか。描くなら、まとまりの型の中の要素をつなぐ規則を別に定める。
- ユーザー型の中の標準的な型からビューを設ける範囲（どこまで深いフィールドを探すか、配列の中の型を扱うか）は、サーバの変換処理とともに定める。
